## 资料页池与文章采集进程拆分

为避免每次修改采集代码后重新搜索十个账号，本日决定把原来同一进程内连续执行的“资料页预热”和“文章轮询”拆成两个可独立启动的阶段。

### 状态文件边界

- `profile-pool-state.json`：只保存资料页池账号清单、`ready / temporarily_unverified / rebuild_required` 状态、最近预热/附着时间和诊断登记；旧 HWND 与标签位置不能跨进程直接信任。
- 每账号 `watch-state.json`：只保存已知 URL、轮次、最近采集时间、错误和摘要，不再保存 `profile`。
- `scheduler-state.json`：只保存轮询轮数、调度阶段、时间窗口和调度错误，不再保存 `profile_registry`。

读取旧版每账号状态时主动移除遗留 `profile`；读取旧版调度状态时主动移除 `profile_registry / profiles_ready / profiles_unavailable`，防止代码热更新后复用旧进程 UI 标识。

### 独立预热阶段

`--bootstrap-profile-pool` 只执行：

`恢复搜一搜 → 逐个搜索账号 → 验证资料页 → 建立十账号资料页池 → 写 profile-pool-state.json → 保留微信标签并退出`

该阶段不刷新资料页、不打开文章、不采集正文。独立预热进程只写 `profile-pool-state.json`，不创建或更新每账号 `watch-state.json` 和 `scheduler-state.json`。

### 热更新采集阶段

`--watch-existing-profile-pool` 默认微信中已经存在十个已知账号资料页和一个搜一搜标签。新进程启动后：

1. 通过本地 OCR 扫描现有标签并重新登记资料页；
2. 不信任状态文件中的旧 HWND；
3. 不在启动附着失败时自动搜索或全量重建；
4. 未附着账号保持 `temporarily_unverified`，本轮跳过，其他账号继续；
5. 成功附着后进入原串行刷新与文章采集流程。

因此热更新操作固定为：停止采集进程但不关闭微信 → 更新代码 → 使用同一输出目录启动 `--watch-existing-profile-pool` → OCR 重新附着现有资料页池 → 继续轮询。

## 资料页恢复与同账号定向去重方案

### 1. 每轮结束前主动归位

保留资料页状态前执行：

1. 确认当前仍为本账号资料页；
2. 执行 `Ctrl+Home`；
3. 等待页面连续两帧稳定；
4. 再保存资料页状态和账号登记。

不采用“每次切换标签后立即刷新”的方案。刷新仅用于明确需要更新内容或恢复页面的阶段，不能作为页面身份识别的前置条件。

### 2. 资料页采用两层识别

第一层只识别资料页结构：

- 不存在搜一搜页面证据；
- 同一导航行至少出现 `全部 / 贴图 / 文章 / 视频号` 中的两个。

若资料页结构成立，但账号名称因滚动不可见，则执行：

`Ctrl+Home` → 等待连续两帧稳定 → 再进行账号名称精确匹配。

第二层确认账号身份：

- 账号名称精确匹配；
- 资料页导航结构成立。

身份确认不再强制要求出现 `公众号`、`服务号`、`私信` 或服务简介。

### 3. 恢复搜一搜时同时识别目标资料页

查找搜一搜标签的每一步，均先判断当前标签是否为目标账号资料页。若是，则立即停止搜一搜恢复，重新登记该资料页并继续轮询，不能继续报“未找到搜索框”或重新搜索该账号。

### 4. 加载中间态留在当前标签重试

切换标签后先等待连续两帧稳定，再执行 OCR。空白页、加载动画、仅识别到 `Q` 或极少文本等状态视为加载中间态：

- 在当前标签进行有限次数重试；
- 不立即切换到下一个标签；
- 不将其直接判定为账号资料页缺失。

### 5. 同账号重复资料页定向处理

扫描到同一账号多个资料页时：

1. 选择第一个完整校验成功、能够正常刷新或采集的标签作为主标签；
2. 更新 `profile_registry[账号名]` 指向该主标签；
3. 后续标签只有同时满足以下条件才允许关闭：
   - 账号名称精确匹配；
   - 资料页结构成立；
   - 不是文章页；
   - 不是搜一搜页；
4. 其他账号资料页、搜一搜标签一律保留；
5. 无法确认身份的未知标签保留并记录，不自动关闭。

日常恢复顺序固定为：

`单账号恢复 → 同账号定向去重 → 其他标签不动`

### 6. 账号状态与重建门槛

账号状态拆为三级：

- `ready`：资料页标签已经确认，可以轮询；
- `temporarily_unverified`：可能处于滚动、加载或 OCR 暂时失败，先在本地恢复并稍后重试；
- `rebuild_required`：完成一整圈可靠扫描后，确认资料页确实不存在，才允许重新搜索建立。

附加约束：

- 同一账号同一时间只能执行一次重建，使用账号级重建锁；
- 新建资料页前必须再次扫描现有标签；扫描中找到目标账号后立即取消新建；
- 暂时识别失败不得直接升级为 `rebuild_required`。

### 7. 判断完整扫描一圈

不再以固定扫描 32 次作为“标签不存在”的正常判据。完整扫描应当：

1. 从已确认的搜一搜工作面开始；
2. 逐个执行 `Ctrl+Tab`；
3. 每个标签等待连续两帧稳定后识别；
4. 再次回到同一个搜一搜工作面时，才确认完成一圈；
5. 较大的扫描次数上限只用于防止死循环，不能作为正常结束条件。

如果无法可靠确认已经绕行一圈，则账号进入 `temporarily_unverified` 并稍后重试；不能宣称资料页不存在，也不能立即重新搜索。

### 8. 全量清理的使用边界

全量清理只作为人工维护手段，适用于：

- 标签数量严重失控，所有账号平均需要扫描几十次；
- 搜一搜标签无法可靠定位；
- 无法区分文章页、资料页和未知页；
- 多数账号同时进入 `rebuild_required`；
- 虚拟机或微信重启，原标签登记整体失效。

单个账号资料页需要重建时，不允许清空其他九个账号、搜一搜或未知标签。

## 下午轮询延迟问题的阶段性判断

现有日志表明，延迟主要来自异常恢复路径，而不是 300 秒轮询参数本身：

- 资料页已存在，但短暂 OCR 失败后进入搜一搜恢复；
- 在大量标签间重复扫描，且固定次数扫描不能证明已经完成一圈；
- 目标资料页在恢复扫描中被忽略，随后重复搜索并打开同账号标签；
- 加载中间态被快速切走，触发更多恢复和重建；
- 文章标签返回、资料页重新登记和重复页处理失败，造成分钟级重试。

因此当前优先级为：先修复资料页识别、恢复状态机和定向去重链路，再进行常规性能优化。上述稳定性修复本身就是目前收益最大的延迟优化。

稳定性修复后，应先完成一轮干净的十账号基线测试，并记录以下阶段耗时：

- 标签切换与稳定等待；
- 资料页身份确认；
- 页面刷新；
- 资料页文章卡片 OCR；
- 文章打开、解析和关闭；
- 返回资料页；
- 恢复扫描与重建。

基线稳定前暂不建议降低轮询间隔、增加同虚拟机并行任务或扩大账号数，否则会放大鼠标键盘竞争、重复标签和误重建问题。

## 资料页匹配后的 OCR 短路优化

当前启动阶段可见页面路径仍保持：

`搜一搜 → 目标资料页 → 搜一搜 → 下一个目标资料页`

这是依次建立十账号资料页池的正常预热流程，不做删除或改写。性能问题发生在同一资料页截图的内部判定顺序：账号名称和资料页结构已经精确匹配后，代码仍继续对该截图执行搜索框、账号分类和搜一搜首页 OCR，造成资料页无操作停留时间增加。

本次确定并实现以下顺序：

1. 等待当前标签连续两帧稳定；
2. 执行目标账号名称与资料页结构校验；
3. 若精确匹配，立即返回成功，不再执行搜一搜页面检测；
4. 只有资料页不匹配时，才检测搜一搜工作面、加载中间态和完整绕圈锚点。

该调整不降低安全性：资料页身份校验本身已经要求精确账号名称、资料页导航结构成立且不存在搜一搜证据。它只删除成功路径上的重复 OCR，不改变预热页面路径、失败恢复、重建门槛和同账号定向去重规则。
