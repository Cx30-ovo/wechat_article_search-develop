# 虚拟机部署与跨平台适配边界

> 本文说明部署决策，不替代 `WECHAT_SEARCH_COLLECTION_FLOW.md`。微信采集的页面顺序、校验条件、恢复逻辑和测试预期，只以当前流程基线为准。

## 1. 当前结论

当前采集器依赖 Windows 微信桌面客户端和可交互的 Windows 桌面。Windows API 负责窗口句柄、DPI、剪贴板、截图以及鼠标键盘控制，因此当前版本不能直接迁移到 Linux 或 macOS 虚拟机。

| 方案 | 当前兼容性 | 资源与扩展性 | 建议 |
|---|---|---|---|
| Windows 11 虚拟机 | 最高，当前生产基线 | 单实例负担较高 | 现在上线或优先保证稳定时使用 |
| Linux ARM64/x86_64 + X11 | 尚未完成适配 | 通常更适合多实例，但需要实际压测 | 作为下一阶段移植目标 |
| macOS 虚拟机 | 尚未完成适配 | 多实例管理和系统权限成本较高 | 不作为默认方案 |

这里的“Linux 负担较小”是部署方向上的判断，不代表当前项目在 Linux 上已经稳定。实际负担还取决于微信客户端、浏览器渲染、OCR、模型请求、虚拟显示器和账号数量，必须以目标宿主机实测为准。

## 2. Windows 11 生产部署

Windows 11 是当前唯一应直接用于生产的虚拟机系统。固定以下因素后再做连续验收：

- 微信客户端版本；
- Windows 版本和补丁；
- 虚拟机 CPU、内存和磁盘；
- 分辨率、缩放比例和显示器数量；
- 交互式桌面、远程维护方式和锁屏策略。

每台虚拟机建议先从不超过 10 个公众号开始。资料页池建立后，使用独立的 `profile-pool-state.json` 和文章监听状态；代码更新时只重启采集进程，不关闭微信资料页标签，按流程基线执行热更新附着。

## 3. Linux 移植试验

Linux 适合被作为多虚拟机扩展方向，但必须先完成桌面适配层，不能只替换 Python 依赖：

1. 使用与宿主机架构匹配的 Linux 客户端和系统镜像；Apple Silicon 优先使用 ARM64/aarch64。
2. 使用完整图形桌面，优先 X11/Xorg；Wayland 下全局键鼠、窗口和截图权限差异更大。
3. 替换 Windows 窗口枚举、激活、DPI、剪贴板、截图和键鼠输入实现。
4. 重新验证微信搜一搜、标签切换、资料页、文章页和 `Ctrl+W` 返回路径。
5. 在单账号上完成连续闭环后，再验证两账号、十账号和多虚拟机并行。

Linux 试验期间，仍必须遵守当前流程中的页面身份校验和失败证据要求。OCR 识别成功、进程没有报错，不能单独证明页面已经完成正确切换。

## 4. macOS 虚拟机边界

macOS 虚拟机不是当前项目的低成本替代方案。即使能够运行 macOS 微信客户端，仍需重新实现窗口和桌面控制，并处理辅助功能、屏幕录制、剪贴板和输入权限；现有 Win11 页面规则也不能直接复用。只有在必须使用 macOS 微信客户端或已有 macOS 自动化基础设施时，才建议单独评估。

## 5. 多虚拟机验收顺序

推荐按以下顺序扩容：

```text
一台 Windows 11 VM 单账号
        ↓ 连续闭环和异常恢复通过
一台 Windows 11 VM 多账号资料页池
        ↓ 固定版本运行一个完整监听窗口
第二台 Windows 11 VM 并行
        ↓ 资源、网络和 MongoDB 写入压测
Linux X11 VM 单账号移植试验
        ↓ 适配层与流程验收通过
Linux 多 VM 扩展评估
```

每增加一台虚拟机，都要使用新的输出目录和独立账号分片；不要用两个实例同时登录或控制同一个微信账号。宿主机内存不足、图形桌面被回收、远程桌面导致分辨率变化，都会表现为 OCR 或窗口控制不稳定，不能简单归因于网络问题。

## 6. 与当前流程的关系

Win11 搜索提交、失焦确认、资料页身份确认、文章标签关闭、URL 去重、资料页池热更新和恢复扫描，统一以 [`WECHAT_SEARCH_COLLECTION_FLOW.md`](./WECHAT_SEARCH_COLLECTION_FLOW.md) 为准。任何 Linux/macOS 适配都必须在对应平台重新建立等价的证据和测试，不得仅凭 Windows 测试结果宣称跨平台稳定。
